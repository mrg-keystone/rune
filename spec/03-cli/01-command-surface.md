## Command surface

| Command | What it does |
| --- | --- |
| `rune init <name>` | Scaffold a fresh **composed monorepo**. `<name>` names the new project: rune creates a `<name>/` directory under cwd and scaffolds the whole composed monorepo inside it — every path below (`ui/`, `server/`, `spec/`, the git-root `deno.json`/`serve.ts`) is written under `<name>/`, and `<name>` is also recorded as the workspace's `deno.json` `"name"` field. This directory-creation behavior is settled independent of the composed-monorepo git-root-ownership question below: `rune init` behaves like a conventional scaffolder, creating and scaffolding into its own `<name>/` directory regardless of how git-root ownership is eventually resolved. `rune init` is **create-once, not re-runnable**: rune errors (exit 1, no writes) if `<name>/` already exists and is non-empty, rather than overwriting or overlaying into it; a bare, already-existing empty `<name>/` is the one exception and scaffolds normally. The idempotent-write and merge phrasing below (`spec/manifest.json` written idempotently if absent, the engine import map merged into `server/deno.json`, the workspace `deno.json` `"name"` field set) does not describe tolerance for a second `rune init` invocation — it describes rune's own overlay step, later in the *same* init run, re-touching files sprig (or rune itself, in the sprig-absent path) already wrote earlier in that run: idempotent-if-absent and merge-not-clobber are how rune avoids stepping on sprig's output when composing the two halves of one scaffold, not a general re-run contract. A second, separate `rune init <name>` against an already-scaffolded `<name>/` hits the non-empty-directory error above. When the sprig CLI is present — the binary probed on `PATH` then at `~/.deno/bin/sprig` — rune shells out for the `ui/` half (`sprig init ui/` — sprig's argument is the target directory to scaffold into, not a project name; a failed sprig run → exit 1 with its output), and the sprig scaffold writes the git-root `serve.ts` composition root (`Deno.serve(Backend(Frontend))`) and the workspace `deno.json`. **When sprig is absent, init degrades gracefully instead of exiting**: rune scaffolds the backend, writes the neutral git-root files itself (the workspace `deno.json` and the same `serve.ts` composition root sprig would write, `Deno.serve(Backend(Frontend))` — it still imports `Frontend` from the not-yet-scaffolded `ui/`, so the composed app is non-runnable until the user runs `sprig init ui/`; keep alone remains runnable via `server/bootstrap/mod.ts`), lays down the shared `spec/` skeleton, and emits a marker telling the user to add the UI half with `sprig init ui/` (install sprig first via `deno run -A jsr:@sprig/core/cli install` if needed). Either way rune overlays the keep backend — `server/bootstrap/`, shared `spec/{runes,misc,ui}/`, a starter `spec/runes/core.rune`, and a durable `spec/manifest.json` (the durability manifest — see [01-architecture.md](../01-architecture/00-overview.md) — written idempotently if absent) — merges its engine import map into `server/deno.json`, and sets the workspace `deno.json`'s `"name"` field to `<name>` (sprig's `deno.json` output has no name, since sprig only receives the target directory; in the sprig-absent path this is a no-op, since rune already wrote that field when it wrote the file itself). Records the layout decision in `spec/misc/layout.md`. Which repo owns the composed-monorepo git root is an open cross-repo decision ([DECIDE] — coordinated in tooling/coms.md). (`src/rune/entrypoints/init/mod.ts`) |
| `rune sync <file.rune>` | The reconcile pass: step 1, **Plan** (parse + validate the spec), then scaffold/prune/preserve the generated tree — full step-by-step semantics in [02-rune-sync-semantics-that-matter.md](02-rune-sync-semantics-that-matter.md), the generated-tree shape in [04-codegen.md](../04-codegen/00-overview.md). |
| `rune check <file.rune>` | Validate only — same step 1, **Plan** (parse + validate), errors as sync, zero writes. Exit 0 clean / 2 errors. This is the plain, default check — the one `rune dev` runs every cycle ([03-rune-dev-the-live-loop.md](03-rune-dev-the-live-loop.md)) — and it does not touch the contract. `rune check --contract` is a distinct, opt-in mode (CI's job, not the dev loop's): it recomputes the contract's provenance stamps — `openapi.json ← src/<module>/**` and `client/ ← openapi.json` — defined in [04-codegen/02-the-contract-artifact-spec-contract.md](../04-codegen/02-the-contract-artifact-spec-contract.md) — and exits 2 on a mismatch, a read-only drift check consistent with this command's zero-writes contract. The drift check verifies the whole composed backend tree against the committed `spec/contract/` output, not the single `<file.rune>` argument — that argument still scopes the parse+validate step, but `--contract`'s drift check is independent of it. Before any contract-emission pass has run, `spec/contract/` doesn't exist yet, and `--contract` is a no-op (exit 0, nothing to verify) rather than a failure. (`src/rune/entrypoints/check/mod.ts`) |
| `rune manifest <file.rune>` | One-shot generate — sync's step 1, **Plan** (parse + validate), plus the create/regenerate writes, **and nothing else**: no create-once growth, no `deno.json` merge, no bootstrap regen, no ghost stubs, no heal rules, no diagnostics, no prune, no run-all gate. `[--root <dir>] [--artifact <keywords.json>] [--json]` — same two flags, same defaults, as `rune sync`'s [`--root`/`--artifact`](02-rune-sync-semantics-that-matter.md): absent `--root`, the codegen root is derived from the spec's own path (never cwd); `--artifact` plans from an edited language artifact — its bindings, codegen templates, and policies — instead of the engine defaults, and an unreadable or invalid artifact exits 2. `--json` prints one object — `{ module, rune, created, regenerated, appended, skipped, errors }` (root-relative path arrays; `appended` is always empty; `errors` collects I/O failures) — or, on failure, exactly one of three error objects: `{ error: "io", path, message }` for an unreadable spec, `{ error: "artifact", path, message }` for an artifact file that can't be read or isn't JSON, `{ error: "parse_error", rune, errors }` for spec validation errors. Two failures ignore `--json` and print plain text to stderr: a usage error (argument parsing fails before the flag is honored) and an artifact that parses as JSON but fails artifact validation (`loadArtifact`'s `invalid <path>:` diagnostics). Exit 0 on success; 2 on every failure above and on any write I/O failure (a non-empty `errors` array in the success shape). (`src/rune/entrypoints/manifest/mod.ts`) |
| `rune lint [dir]` | The architecture linter — 27 rules over the project tree (see [05-linter.md](../05-linter/00-overview.md)). `[dir]` (default `.`) is the start point, not the walk root: lint walks **up** to the nearest `deno.json(c)` (falling back to `[dir]` when none is found), then descends into `server/` when that root has no `src/` of its own but holds `server/bootstrap/mod.ts` — so run at a composed-monorepo git root it lints `server/`, never `ui/`, and `server/` (not the git root) *becomes* the lint root for the rest of the run. Finding paths are relative to that lint root — `server/` itself once descent happens — which is what lets `--module` below match `src/<name>/` paths even in the composed-monorepo case. Flags: `--strict` (sets `RUNE_LINT_STRICT=1`, also honored as the alias `RUNE_STRICT`, for strict-gated rules — currently only `rune-heal-todo`, silent in a plain lint but failing under `--strict` on any heal-rules entry still carrying `todo: true`; it adds findings, so it can only turn a clean exit into a violating one, never the reverse — see [05-linter.md](../05-linter/00-overview.md)), `--module <name>` (scopes the report, not the walk: every rule still runs over the whole lint root, then only findings whose path is under `src/<name>/` are printed and counted toward the exit code), `--json`, `--no-suggest`. Exit 1 on any violation. |
| `rune dev [path]` | The live loop: watch → check → sync → restart the app under `KEEP_DEV` — the status-file env var and the full watch/cycle/registration semantics are defined in [03-rune-dev-the-live-loop.md](03-rune-dev-the-live-loop.md). |
| `rune stop [path]` | Stop this repo's shared `rune dev` process and reap its app child. Nothing registered for the repo → a "no shared dev process registered" notice, not an error. Always exit 0. |
| `rune validate <keywords.json>` | Meta-validate a language artifact against the artifact contract — the `keywords.json` format and its contract are defined in [08-language-tooling.md](../08-language-tooling/00-overview.md). `[--json]` prints `{ ok, errors }`, each error a `{ path, message }` pair; usage/read/parse failures print plain text regardless. Exit 0 valid / 1 invalid / 2 on a usage error or an unreadable/unparseable file. |
| `rune lsp` | Start the language server (delegates to the Rust `rune-lsp` binary). |
| `rune fmt` / `format` / `install` / `uninstall` / `completions` | Fast authoring commands — verbatim passthrough to the Rust `rune-syntax` binary (formatting, editor integration, shell completions). This passthrough list does not include `validate`: the per-file, CI-friendly spec syntax check (parse errors plus the 80-column limit — a narrower, non-interactive counterpart to `rune-lsp`'s diagnostics) has no `rune` subcommand and is invoked directly as `rune-syntax validate <file.rune>` — distinct from `rune validate` above, the artifact meta-validator (see [08-language-tooling/03 § `rune-cli`](../08-language-tooling/03-the-rust-workspace-lang-parser-lsp-cli.md)). |
| `rune update [tag]` (alias `upgrade`) | Self-update from GitHub Releases on `mrg-keystone/rune`: fetches the target release's own `install.sh` asset — `[tag]` defaults to the rolling `latest` release; `main`'s `scripts/install.sh` is the fallback for releases predating the asset — and runs it: binaries, Claude skills *and* agents. |
| `rune -v` / `version` | Prints the baked version/commit (`src/core/dto/version.gen.ts`) and checks the `mrg-keystone/rune` `latest` release's `commit.txt` asset for a newer build (asset, not tag — gh rolling releases freeze the tag but swap assets). |

Dispatch notes: the first argument must be one of the commands above. There is
no bare-directory shorthand — the linter always runs as `rune lint [dir]`
(`rune .` is an unknown command) — and a bare `foo.rune` argument is **not** a
sync shorthand: it errors with a `sync`/`check` hint. Both cases exit 2; bare
`rune` with no args prints the help (exit 0). Rust helper binaries are resolved
by probing `RUNE_BIN_DIR`, the directory next to the installed `rune`,
`lang/target/{release,debug}/`, then `PATH`.

From a checkout, run without compiling: `deno run -A src/bootstrap/mod.ts <args>`.

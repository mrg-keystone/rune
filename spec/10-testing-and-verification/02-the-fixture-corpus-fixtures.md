## The fixture corpus (`fixtures/`)

Most subtrees below are either a fresh input a gate reads each run, or a
captured baseline compared against fresh output; three (`specs/`, `bullshit/`,
`eval/`) are ungated — `bullshit/` and `eval/` serve the scope/spec skills;
`specs/` has no current consumer (see its row). The
table is the transpose
of [the verify ladder](01-the-verify-ladder-deno-task-verify.md)'s Gate |
Proves table: read a row here to answer "if I edit this fixture, which gates
break and which golden do I recapture?"

| Subtree | Holds | Consumed by / recapture |
| --- | --- | --- |
| `corpus/valid/` (20) | Full tag coverage, all boundary prefixes, faults 0/1/many, polymorphism single/many/nested, `:core`, static vs instance, inline DTOs, multi-module, a realistic `example-e2e`. One documented lenient gap: `poly-nested.rune` (a `[PLY]` inside a `[CSE]` — spec-illegal, parser accepts; owned by the WO-4c/4d follow-up). This is the ladder's spine — the single input set behind six gates: **L0**, **L2**, **L3**, **L4**, **L5**, **L7**. | **corpus** (accept verdict) · **L0** (parse + manifest determinism — byte-identical across two runs, no golden) · **L2** (one `golden/parse/<spec>.json` each) · **L3** (one `golden/manifest/<spec>.json` each) · the source of the three `[MOD]` specs (`module-billing`, `module-catalog`, `entrypoint`) that materialise into the `projects/<spec>/` trees **L4** lints and drive **L5** and **L7** — recapture parse/manifest/lint goldens with `--update-goldens` (editing a `[MOD]` source spec invalidates its `golden/lint/<spec>.json` too) |
| `corpus/invalid/` (14) | The parser's error paths. | **corpus** gate only (reject verdict) — no goldens exist for `invalid/`, nothing to recapture |
| `golden/parse/` | One AST golden per `corpus/valid/` spec (20). | **L2** — recapture with `--update-goldens` |
| `golden/manifest/` | One planned-file-tree golden (paths + content) per `corpus/valid/` spec (20). | **L3** — recapture with `--update-goldens` |

| `projects/module-billing/`, `projects/module-catalog/`, `projects/entrypoint/` | Three trees **materialised** respectively from `corpus/valid/module-billing.rune`, `corpus/valid/module-catalog.rune`, `corpus/valid/entrypoint.rune` — prove generated output stays lint-clean. | **L0** (`lint --json` determinism, byte-identical across two runs, no golden) · **L4** (lint targets) — regenerated by `--update-goldens`; the same three source specs separately drive **L5**'s live Studio-vs-engine comparison and **L7**'s migration check (see the `corpus/valid/` row) — neither reads these trees off disk; `module-billing` alone is also **L6**'s binding/UI-data-path mutation target, asserting its generated DTO file paths gain a `-dto` segment |

| `specs/` | A full generated composed project with a real `data.json`. | **UNGATED**, no current consumer — not read by any verify gate; despite the name, neither `e2e/` acceptance suite reads it (both are self-contained committed modules with hand-filled coordinator bodies, per [03-acceptance-suites-e2e](03-acceptance-suites-e2e.md)) |
| `bullshit/` | A whole-diamond realistic scaffold (product spec, modules, heal-rules). | **UNGATED** — serves the skills, not read by any verify gate |
| `eval/` | Seed drafts for exercising the scope/spec skills. | **UNGATED** — serves rune:scope/rune:spec, not read by any verify gate |

**One spec traced through the ladder**, `module-billing`:
`corpus/valid/module-billing.rune` parses into
`golden/parse/module-billing.json` (L2), generates into
`golden/manifest/module-billing.json` (L3), and materialises as the
`projects/module-billing/` tree L4 lints; the same source spec, read live
rather than off either golden, is also one of the three inputs L5 diffs
(Studio `generate` vs the engine's `planManifest`) and one of the three L7
migrates the N-1 artifact against. Every `corpus/valid/<spec>.rune` carries
this same 1:1 shadow — a `golden/parse/<spec>.json` and a
`golden/manifest/<spec>.json`; only the three `[MOD]` specs additionally
materialise into a `projects/<spec>/` tree and feed L5/L7.
